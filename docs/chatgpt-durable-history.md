# ChatGPT durable customer history

Conversations are now encrypted in `chatgpt_history_threads`, owned by a permanent TopRated user ID. Orders, grants and launch sessions are not history owners. Expiring an entitlement still denies every proxy route (including Saved chats); renewing the same TopRated account restores access. No expiry cleanup deletes these records.

Links associate each saved thread with the actual upstream user identity (hashed `/api/auth/session` user ID) and upstream conversation UUID. Changing a login inside Account 1 is distinct from rotating its cookies; changing assignments is also supported. There is no automatic fallback to a different paid account.

The original ChatGPT UI and streaming remain available. A **Saved chats** link opens a private local transcript. Old saved threads appear in fetched history pages even when the replacement account has no provider history. A foreign-account `/c/id` opens the saved transcript with **Continue this conversation**. Continuing opens the native composer; the user's next text question is sent along with the saved text as quoted user context. A tab-specific, session-bound, short-lived, single-use token connects the new upstream conversation to the same saved thread. Stream resumption can resolve its saved thread before the first provider snapshot becomes available. The browser bridge handles both backend API paths and the native hostname-dependent `__codex-api` paths. Hidden provider analysis is excluded from displayed and replayed messages. This is a new upstream thread, not a claim that ChatGPT migrated a thread between accounts. The transcript retains the original user messages rather than showing replay wrappers. History captures the full provider mapping after successful streamed replies, on interrupted streams when possible, and when opening an owned conversation. No foreign or unowned upstream conversation is imported.

The text context limit is 90,000 characters. Longer chats receive an explicit request to copy the needed section. With `CHATGPT_ATTACHMENT_HISTORY=1`, accessible documents, file-service images and sandbox downloads are copied to a separate private bucket as encrypted, owner-bound objects. Saved chats lists private downloads with explicit pending/unavailable states. Continuation reuploads the selected branch's saved attachments to the currently assigned official login and references the new file IDs. No old account token or signed URL is replayed. Missing/unsupported assets fail explicitly rather than silently dropping context. Each binary is limited to 25 MiB; automatic continuation restores at most ten assets totalling 25 MiB. Larger sets remain downloadable individually. Audio/video and non-file-service image pointers are currently unsupported and require reattachment. Archived branches remain in the encrypted mapping. The Saved chats page displays the selected branch.

Before Admin replaces or revokes a stored login, a backup pass runs against explicitly owned conversations. A failed pass prevents the change; it does not delete or overwrite history. If the old login has expired, replacement is allowed when every owned chat already has either a saved transcript or an explicit prior upstream-missing record; unknown unsaved chats require refreshing the old login first. Initial import must finish before activation. Back up the encryption key alongside the existing private production environment; do not commit it. The current encryption envelope is shared with the existing AES-GCM vault with a checked history-specific domain/user/thread payload.

## Release procedure

1. Apply `20261117090000_chatgpt_durable_history.sql` from the GitHub release. It creates four isolated tables with RLS enabled, accessible only to the server service role. No balances, existing orders, other tools or source history rows change.
2. Use the existing production dependency snapshot. Run the ChatGPT suites, `tsc --noEmit` and the production build. The npm lock file is already inconsistent with package.json; do not install new production dependency versions during this release.
3. Run `bun scripts/chatgpt-history/backfill.ts` under the current private production environment. It prints counts only. Transient errors block activation. Pre-existing upstream HTTP 404s are recorded separately in a service-only backup issue ledger and shown as unavailable on the owner’s Saved chats page; they are never presented as successfully backed-up transcripts. Retain the current official account until all accessible chats have been captured.
4. Run `scripts/chatgpt-history/deploy.py` from a clean GitHub checkout. It starts new main/Admin and ChatGPT processes on two unused local ports, validates both before changing only their two vhosts, and keeps previous processes running. Dedicated Claude, Grammarly, StealthWriter, Phrasly and QuillBot processes/vhosts stay in place.
5. Verify fresh launches, private transcript reads, no cross-user reads, expired access rejection, renewed access and continued text history. Account 2 requires its own configured login before claiming two different live provider logins were tested.

Rollback: restore `/home/ubuntu/deploy-backups/chatgpt-history-20261117/topratedseotools` and `chatgpt-proxy` to their enabled Nginx paths; validate and reload Nginx. Keep the additive tables and all saved transcripts. The prior code ignores these tables. Do not remove history to roll back.

Validation: `tests/chatgpt-durable-history.test.ts` exercises two-user encrypted capture, expired/renewed access, same-slot upstream identity replacement, saved-history merge, complete text continuation, tab/session-bound one-use tokens, repeat snapshot merging without cycles, file/length refusals, and database failure. Existing ChatGPT proxy, isolation, vault, controls and account-routing suites must also pass.

## Attachment release

Apply `20261117090001_chatgpt_private_attachments.sql`. It adds two server-only tables and a private encrypted-object bucket; it does not alter existing data or client storage policies. Preserve the existing encryption key. Keep both features off in unrelated provider processes.

Before activation, run the ChatGPT suites and production build from the pinned production dependency tree. Run `CHATGPT_DURABLE_HISTORY=1 CHATGPT_ATTACHMENT_HISTORY=1 bun scripts/chatgpt-history/backfill.ts --legacy-attachments` once while the old login remains available. This explicit pre-activation import registers only files referenced in already owned conversations. Never use the legacy import flag as a normal runtime default. All future native uploads and generated assets have provider-identity-scoped writer ownership. File downloads and outgoing file references reject another writer's IDs; the shared file listing is blocked in favour of Saved chats.

Live release gate: validate the provider's current create-upload/PUT/completion/download protocol with disposable files, private storage round trips and two-writer access denial. Confirm a continued native reply can read a restored document and image before claiming end-to-end automatic restoration. A simulated old identity is not a second configured provider account; Account 2 remains unconfigured unless separately connected.

`deploy-attachments.py` starts isolated main/Admin and ChatGPT candidates, retains previous processes, switches only those two vhosts and saves the immediately previous configs under `/home/ubuntu/deploy-backups/chatgpt-attachments-20261117`. Before switching, retain hashes for the other provider configs and confirm they are unchanged afterward. Roll back using those saved configs, validate/reload Nginx and retain every attachment object/table. Do not delete stored attachments on expiry, account change or rollback.

Stream-end attachment copies run after the reply without delaying final tokens. Account replacement first drains that queue, then synchronously retries current-account backups. Transient attachment failures block replacement; an expired old login cannot bypass pending or unaccounted attachment records. Pre-existing expired/missing sources have explicit unavailable entries; they are not reported as saved. Supported references on the visible branch are downloadable even if the upstream login is later disconnected. Storage failures never silently downgrade a ready backup.

# Phrasly limits in the main Admin customer flow

StealthWriter was traced from Admin → Customers → select customer to StealthWriterControlsCard in admin.customers.$userId.tsx, its React Query state/mutation handling and its authenticated Admin server functions. Phrasly now follows that customer-scoped placement and interaction pattern: PhraslyCustomerControlsCard appears immediately after StealthWriter AWS controls and before ChatGPT controls. It has the same card and two-column feature-panel layout, numeric daily limits, per-feature save feedback and invalidation/refetch after a successful save. Unlimited and Remove limit retain the existing Phrasly semantics.

Each write calls the existing /ext-admin set_limit action with the selected customer UUID and feature. Its owner verification, value validation, single-grant update and audit event are unchanged. Current usage, access dates, revocations and the user's other feature remain intact. Customers without Phrasly feature grants are shown assignment guidance, with no implicit access creation. Refresh Phrasly limits reloads after a new assignment.

The source customer route imports this reusable card directly. Production currently hosts the main Admin app separately from Phrasly. A small first-party bridge mounts the exact same card after the existing StealthWriter card, so the current Admin deployment gains it without replacing its Turnitin, customer, billing or other product modules. It follows client-side customer navigation, unmounts stale roots and avoids duplication when the native card is present. The bridge is loaded only through the two existing main Admin nginx locations; the standalone Phrasly page and customer-facing site are unchanged. Existing analytics injection is preserved.

Build: node scripts/phrasly/build-admin-customer-controls.mjs. Regression: node tests/phrasly-admin-exporter/customer-controls-browser.cjs. The seven real Chromium checks cover position, Unlimited, bounds, save targeting, removal, remounting across customers and cleanup away from customer pages. Production live verification opened the real customer page, confirmed placement and both Unlimited values, saved the existing Unlimited Humanizer setting for that selected customer, and observed the refetched saved value. No page errors or provider generation requests occurred; the temporary owner session was revoked locally.
